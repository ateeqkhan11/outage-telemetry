About this page

This page sets out the rules as designed. It is generated from the rules file, so every number below is the number the index uses. The rules are a draft until an independent reviewer has checked them. What the index covers today is listed separately, with dates, under Current scope.

What counts as down

Two definitions are reported side by side, so a policy can name the one it uses.

Hard down

At least 2 companies each see 90% or more of their calls to a Service fail over the last 3 minutes.

A call counts as failed when it gets a server error (HTTP 5xx), a timeout, no connection or throttling (HTTP 429 or an AWS throttling error such as ThrottlingException). Throttling is the one client error that counts. Any other client error (HTTP 4xx, such as bad credentials) shows that AWS answered, so it never counts. The Services checked are S3, DynamoDB, Lambda, EC2 and STS, in us-east-1.

Rules version 1-draft-rolling

Two companies must see it

A Service is down only when the probe networks of at least 2 companies each see it fail, by the definition above, at the same time. One company’s view is never enough.

Networks run by the same company count once. Each counted network in scope today is run by a different company: GitHub Actions by Microsoft and Cloudflare Workers by Cloudflare.

A probe network’s view counts only while its own connection works. In every round it also calls a site outside AWS. If that call fails, the problem is on the probe’s side: the round is set aside and is not counted as an AWS failure.

Rules version 1-draft-rolling

When an outage starts and ends

An outage starts in the first minute the rule above calls a Service down. It ends at the last minute called down, once 3 later minutes have been called up, with no further minute called down.

The duration runs from the first minute called down to the last, inclusive. It is read against waiting periods of 1 h and 2 h.

Rules version 1-draft-rolling

Timing and counting

  • All times are UTC. Every check is filed under the UTC minute in which it was made; minutes start at :00 seconds.
  • Each probe network makes 6 rounds of checks a minute by default, evenly spaced. A round is one call to each of the 5 Services plus the call to a site outside AWS.
  • A company’s share of failed calls to a Service is worked out over all the usable calls its networks made in the window of the definition (3 minutes for Hard down and 10 minutes for Degraded), counting back from the current minute.
  • There is no minimum number of calls. A single usable call in the window is enough for a company to be judged for that Service.
  • Each Service is judged on its own. The region is down while any Service is down, up only while every Service is up, and otherwise not enough data.
  • Minutes with not enough data between the first and last minute called down stay inside the outage and count toward its duration, and so toward the waiting period. They do not end it. Minutes with not enough data after the last minute called down do not extend it.

Rules version 1-draft-rolling

The reference network is shown, never counted

The reference network (AWS Lambda, Oregon (us-west-2)) runs inside AWS. Its results are shown for reference but never counted, because a probe inside AWS cannot judge AWS independently.

Rules version 1-draft-rolling

Enough data, or no call

An official call needs 2 companies, each covering 95% or more of the last 24 h and each reporting within the last 15 minutes.

If that is not met, the state is “not enough data”. Missing data is never treated as up.

Rules version 1-draft-rolling

When it does not fire

Worked cases where the rules do not call an outage.

  1. One company’s network failsA Microsoft-run probe sees Lambda failing; Cloudflare’s sees it working. Only one company sees it, so it is not down. If one company’s probe is down altogether, its rounds are set aside, and with fewer than 2 companies reporting the state is not enough data.
  2. The reference network failsThe AWS-hosted reference probe sees failures that the counted networks do not. It is never counted, so no outage is called.
  3. A status page reports an incidentAWS posts an incident, but the counted networks’ calls keep succeeding. With no measured failure there is no outage.
  4. Crowd reports spikeReports of problems rise on public sites, but the counted networks’ calls keep succeeding. Reports are not measurements, so no outage is called.

Rules version 1-draft-rolling

Why clocks differ

A provider’s status page starts its clock when an incident is posted and stops it when the incident is marked resolved, after the provider’s own checks. Crowd reports start when enough people notice and say so. Outside measurement starts when calls from outside fail under a stated rule.

The three can disagree on both the start and the end, sometimes by a long way, and a policy with a waiting period turns on exactly those times. These rules are written down so anyone can see how this clock is read.
